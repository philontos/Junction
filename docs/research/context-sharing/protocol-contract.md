# Context 资产协议：核心契约草案

日期：2026-10-31；状态更新：2026-11-01。状态：待验证的协议候选，尚未决定是否采用，未发布 schema 或实现。先完成[原生存储与生命周期分析](native-storage.md#9-原生完整性与生命周期复核)，再由转换实验确定是否需要本层。本文中的“必须”仅约束候选方案，不表示产品已确认或系统已经满足。

本文落实[稳定性优先架构](architecture.md)，先固定身份、依赖、完整性、提交与兼容语义。JSON 字段拼写和大小阈值在验证后统一冻结，暂不发布一个容易被误认为稳定 v1 的大 schema。

## 1. 协议分层

| 层 | 使用的契约 | 我们补充的语义 |
|---|---|---|
| 内容对象 | OCI Descriptor 1.1.1 | 存储域、访问授权、对象状态与依赖闭包 |
| 采集事件 | CloudEvents 1.0.2 的 structured JSON | 来源流身份、原件定位、采集位置与格式版本 |
| 资产清单 | JSON Schema 2020-12 描述的自有小模型 | revision、coverage、依赖分类与来源关系 |
| 派生解释 | 独立版本的 Projection profile | 有效历史、映射、损失、可用性与适配器能力 |
| 服务操作 | HTTP RFC 9110、RFC 9457 | 提交、读取、并发更新、发布和撤销的领域规则 |

这是对现有标准的组合与收窄，不宣称 CloudEvents/OCI 已定义 Agent Context，也不要求采用它们的全部传输协议或运行基础设施。

## 2. 身份的含义必须唯一

| 身份 | 表示什么 | 不能替代什么 |
|---|---|---|
| Context ID | 一个长期资产的稳定身份 | 会话 native ID、当前版本或某个目录 |
| Revision ID | 一次不可变提交的身份 | 自动变化的 latest/head |
| Manifest digest | 已封存清单的具体字节 | 作者真实性、读取权限 |
| Source / stream ID | 指定来源实例中的一条流；包含必要的 generation 区别 | 文件路径、cwd、provider session ID 单独一个值 |
| CloudEvents `source + id` | 指定来源中的一次事件；重发保留身份 | 时间戳排序、跨租户身份认证 |
| Native ID | provider 自己的关联证据 | 我们所有事件的全局唯一 ID |
| Projection ID / digest | 指定输入、规则与输出的解释产物 | 原件身份 |

服务端的实际唯一性检查还必须包含认证得到的来源/租户命名空间。同一第三方字符串不能让两个租户的数据相互覆盖。

同文本可以发生多次；同 native ID 也可能因分段、重放或更新再次出现在来源中。采集器以已持久化的来源位置和身份协议处理重试，不用“文本相同”或“UUID 相同”作为所有来源的通用删除规则。[CloudEvents 事件身份依据](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md#id)。

## 3. 内容引用直接采用 OCI Descriptor

引用结构使用规范中的 `mediaType`、`digest`、`size`，不另造一套同义字段。[OCI Descriptor 1.1.1](https://github.com/opencontainers/image-spec/blob/v1.1.1/descriptor.md)。本 profile 的额外约束：

- 初始实现必须支持 SHA-256；保留规范中的算法前缀，不预设所有未来 digest 都等长。未知算法不假装校验成功。
- digest 与 size 针对**实际保存的字节**。UTF-8、换行、空白、压缩前后表示不同，就可能有不同 digest。
- 原生文件字节不经过 JSON 解析再序列化后冒充原件。SDK 提供 JSON 值时，标明保存的是值级表示，不能声称取得原始文件字节。
- 清单一经封存，保留其序列化字节；不依靠读取方重新序列化计算身份。首期不增加全局 JSON 规范化或签名要求。
- 完整对象接收时验证摘要和长度；区间读取必须以已验证对象及范围为前提。不存在的对象不能因为有合法 descriptor 就变成已保存。
- OCI 的可选 URL 或 inline data 字段不构成自动联网/下载授权。首期解析器不自动取任意外部 URL，不把未知对象作为可执行内容。
- size 仍遵守 OCI 的整数语义；实现必须拒绝超出支持范围或 JavaScript 安全整数范围的值，不能悄悄舍入。实际上传限额应明显低于表示上限。

内容仓可以内部压缩或加密，但须说明 descriptor 对应的表示，并在向客户端返回该表示时保证一致。首期不引入多种可互相猜测的 hash 口径。

## 4. Revision 清单的最小语义

清单至少包含以下信息组；这些是边界承诺，不是要求将所有信息放进同一张数据库表。

| 信息组 | 必须回答的问题 |
|---|---|
| 协议身份 | 使用哪个 profile/schema；解释它需要哪些能力 |
| 资产身份 | 属于哪个 Context、哪个不可变 Revision；何时由采集/提交方形成 |
| 来源声明 | Agent/SDK/格式与采集器版本是什么；来自哪条 source stream |
| 内容清单 | 原始流片段、附件和其他必需内容的 descriptors |
| 来源覆盖 | 采集起止位置、连续范围、已确认高水位、缺口、截断、未关闭来源 |
| 关系 | 与先前版本或外部来源是什么关系；哪些是内容依赖，哪些只是 provenance |
| 采集诊断 | 不可读、未知、缺失和部分完成的具体原因 |

一个 revision 必须能在没有原始 cwd、原 Agent 进程和展示数据库索引时，说明自己保存了什么。新 revision 可以重用旧对象的 digest，逻辑上仍须完整列举其依赖；首期不要求从任意长的父版本补丁链才能读到当前内容。

### 4.1 两类引用严格区分

**内容依赖**用于重建当前资产表示，例如选定的原始流片段、图片或工具输出。可发布的可携带版本必须具有完整且已验证的必需依赖闭包。

**来源引用**用于说明派生关系，例如某交接来自一个未授权读取的私有 session。它不会授予读取权，也不自动要求下载整个来源。必要时只向接收方暴露不含私有路径/标题的受控引用，详细映射留在拥有者的审计记录中。

无法取得的外部内容标为 external/unavailable 并给出原因，不作为“已经包含”的依赖。是否因此禁止生成交接，由对应 Projection 的能力契约决定。

### 4.2 避免清单之间的哈希循环

原始 Revision 只指向其来源内容及允许的前序关系；Projection 清单指向已封存的输入 Revision 和自己的输出。**原始 Revision 不反向引用后来生成的 Projection。** 默认投影选择放在可更新的目录关系中。

发布时再固定一个发布清单，引用经过选择/处理的公开 Revision 和所选 Projection。原始版本、派生版本、发布版本形成有向无环的内容依赖。任何清单不得要求先知道自己的最终 digest 才能生成其内容。

## 5. CloudEvents 的使用范围

采集事件的外层遵守 CloudEvents，业务内容放入 `data`，不发明不符合规范的嵌套 extension attribute。事件 `specversion` 为 `1.0`，规范基线为 1.0.2；我们的 profile 版本与之独立。[核心规范](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)、[JSON 格式](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/formats/json-format.md)。

第一类事件只表达“观测/采集到一条原生记录”，其 data 指向原件或已验证 blob 中的明确字节范围，并带来源位置、原生类型/ID（若存在）及采集版本。工具调用、用户消息、有效分支等更细语义由 Projection 解释，不要求核心立即包含全部 Agent 消息类型。

时间需区分：观测事件的发生时间、原生记录报告的时间、服务端接收时间。缺失原生时间不能填上当前时间后冒充原始发生时间。流内顺序由来源位置表达，跨流关系由显式关联表达，不能由时间戳推导可靠总顺序。

存储可以将多个完整 CloudEvents JSON 对象分块装入 JSONL 文件，以降低大量小文件成本。**该 JSONL 容器及其顺序约定由本 profile 定义，不冒称 CloudEvents 自带日志排序或事务保证。** 原生 JSONL 与采集事件 JSONL 是不同产物，必须标明格式。

同一受信来源内，相同 `source + id` 的协议重试必须保留第一次封存的事件表示；若身份相同而内容不同，报告冲突。写入者应在重试前保存发送表示，而不是每次生成新的时间和 ID。

## 6. 不能用一个 complete 布尔值概括所有保证

| 维度 | 所表达的状态 |
|---|---|
| Integrity | 内容摘要/长度通过、失败或尚未验证 |
| Coverage | 明确范围内连续、存在缺口、仅选段、来源仍开放、部分来源未取得 |
| Interpretation | 指定 adapter/version 可解释、部分解释、未知或不支持 |
| Usability | 是否满足某个指定用途，例如可读交接、有效历史、原生恢复 |

这些维度不能互相代替。一个持续写入的会话可以“截至偏移 H 完整”，但会话仍开放；未知事件可以完整归档，但无法承诺重建当前分支；可读文本生成成功也不表示图片已带入目标模型。

覆盖声明必须限定来源、generation 和范围。并行子流分别记录高水位；除非来源提供可信的一致快照机制，不宣称跨所有活跃流的全局同一时刻快照。

原始字节高水位、完整记录边界、已解释位置也须分开。半行可以作为已观测字节保留，但不能成为已成功解析的记录；下一批次必须按来源位置衔接。文件路径、大小或 mtime 单独不能证明内容连续；检测到截断、替换或无法确认的原位重写时，重新确认 generation/重新采集，并记录不确定范围，不能静默接到旧流末尾。

采集与同步进度分开：本地原件和待发送任务落盘后确认 capture；远端提交后确认 remote receipt；投影完成后确认 interpretation。重试保留已确认的身份与字节，清理策略不得越过仍未确认的同步内容。

Projection 输出必须绑定确切输入 digest、adapter/规则版本、配置与诊断，逐项说明保留、归一、损失、不支持或未知。源码无法确认某特性时标未知，不用一个推测的成功百分比掩盖。

## 7. 提交、重试和控制状态

### 7.1 可见性的边界

| 对象 | 状态规则 |
|---|---|
| Blob | 上传中内容不可作为已保存依赖；校验并持久化后可被 revision 引用；后续损坏改变健康状态，不改写原身份 |
| Revision | 构建中的清单对普通读取不可见；原子提交后内容固定；删除通过独立控制状态表达 |
| Head | 指向一个已提交版本的便利指针，可变化；发布和运行输入必须使用固定版本 |
| Projection | 生成中/失败不影响原件可读；成功产物不可原地覆盖；新规则产生新产物 |
| Publication | 准备中不授予外部读取；发布时冻结目标清单；撤销改变授权状态，不变更已发布内容 |
| Grant | 创建、到期、撤销由权威事务目录控制；重新授权产生可审计的新授权记录 |

原件持久化与其可解释性分开。因此带明确缺口的私有 revision 可以被封存；它必须携带缺口，不得以完整有效历史对外展示。发布某种用途的版本，还必须通过该用途的闭包与能力验证。

### 7.2 最小操作契约

以下是操作语义，具体 HTTP 路径可以在实现时统一；幂等不能只依赖某个自定义 header 名称。

| 操作 | 原子性、重试与失败要求 |
|---|---|
| PutBlob | 对指定内容身份重复提交相同字节得到同一结果；摘要或长度不符拒绝；客户端不能先自报 verified |
| CommitRevision | 同一受信命名空间内同 Revision ID、同清单重试返回原提交；同 ID 不同清单冲突；依赖不满足时不提交 |
| SetHead | 使用强 ETag / `If-Match`，在存储事务中完成比较和更新；失败返回 412，不覆盖他人的更新 |
| BuildProjection | 输入固定 revision 与规则版本；结果绑定这些输入；重试不能偷偷换成当前 head |
| Publish | 固定目标发布清单与授权的可见性在事务中建立；对外看不到只有授权、没有完整内容的中间状态 |
| Resolve / Read | 按认证主体和明确 revision/publication 根进行授权及依赖校验；digest 不充当访问令牌 |
| Revoke | 幂等；提交后新的授权判定不得再允许该 grant；响应丢失可查原状态 |

创建 revision 与移动 head 是两个语义操作。即使版本已保存而 head 更新冲突，新版本仍可通过确切 ID 找到；不让一次指针竞争导致内容丢失，也不隐式合并两个分支。

远程请求超时意味着客户端尚不知道结果，应查询原 ID 或用原身份重试；不能直接创建新 ID。需要排队时返回可查询的 operation 状态，只有完成持久化承诺后才能报告 committed。[HTTP 幂等与条件语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)。

### 7.3 错误作为协议的一部分

采用 `application/problem+json`，至少定义稳定的领域问题类型和可定位原因。例如：内容校验失败、同身份不同内容、缺失依赖、不支持必需能力、来源覆盖不足、并发前提失效、配额不足、存储暂不可用。[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)。

错误须说明能否原样重试、应重新读取状态还是需要改变输入。权限失败不能通过对象是否存在、错误细节或缓存命中泄露其他租户内容；具体 403/404 策略在同一 API 中保持一致。错误日志不默认携带原生全文或工具参数。

## 8. 兼容与扩展规则

### 8.1 四个版本不能合并

1. **资产协议/profile 版本**：Context 清单和关系的契约。
2. **来源格式与 CLI/SDK 版本**：捕获了什么原生表示。
3. **Adapter / Projection 版本**：使用什么规则解释原件。
4. **公共标准版本**：CloudEvents、OCI Descriptor、JSON Schema dialect 等。

升级其中一个不自动改写其余版本。尤其不能把更换模型、来源 CLI 升级和数据库迁移当成同一件事。

### 8.2 兼容性策略

- 稳定主版本内保持核心语义不变。初期核心键集合严格校验；可选新信息优先放入有命名空间的 extensions，而不是随意增加顶层字段。
- 可选扩展可以暂不解释，但保存和转发时不得删除。中继尽量传递已封存字节，避免一次 parse/stringify 改写资产身份。
- 影响正确解释的扩展列入 `required_features`。读方不支持时，可按能力仅保存 opaque 内容，但不得继续执行其不理解的重建、交接或发布操作。
- 未知主版本可作为普通未解释对象保存；它不被当成已经通过本版本验证的 Context revision。
- 新必需字段、身份/排序/依赖含义变化、旧值重新解释都属于破坏性变更。以新版本或新 profile 表达，不能仅提高 adapter 小版本掩盖。
- 有歧义的 JSON（例如重复 key）在公共清单层拒绝；原生字节仍可作为 opaque 档案保存。外部 schema URI 不能触发任意网络取回，使用固定、受控的 schema registry。

JSON Schema 负责结构；引用闭包、来源范围、权限、内容 hash、版本依赖由语义验证器负责。不能把“通过 JSON Schema”展示成“Context 完整可靠”。验证器使用明确 dialect 并验证其适用测试集。[JSON Schema 2020-12](https://json-schema.org/draft/2020-12/json-schema-core)、[官方测试套件](https://github.com/json-schema-org/JSON-Schema-Test-Suite)。

### 8.3 变更流程

先增加反例/兼容语料和新 reader，再生成新格式；同时保留旧输入与旧投影用于对照。任何来源适配器更新都不能静默回填覆盖已封存结果。数据库 migration 改变查询结构，也不得擅自重新解释原件或丢弃授权记录。

内部 0.x 阶段也需要明确迁移说明。升到稳定主版本的条件是兼容套件和实际双 Agent、双租户使用通过，不以字段表看起来完整作为发布依据。

## 9. 分享和导入的特殊约束

1. 发布清单引用的内容必须经过选择检查。原始 blob 内夹带未选记录时，重新生成仅含选中内容的发布对象；不能把完整 blob 暴露给接收方。
2. 公开 Projection 基于已选择/处理的公开输入生成；不能复用一个读取过全部私有内容的摘要，然后只删除几句就声称不存在残留泄露。
3. 私有源映射与公开出处分开管理。需要检查本地路径、标题、原始工具参数和 provenance 引用本身是否属于允许发布范围。
4. 接收方输入仍是带来源的历史材料；历史中的 system/developer 指令、工具调用和环境权限不自动获得执行地位。
5. 导入包中的 tenant、owner 和权限声明均不是授权依据。服务端认证与显式 grant 决定访问，新本地资产的所有权由导入操作确定。
6. 重建/导出不得遍历本地任意路径、跟随来源中的符号链接或执行历史命令。协议只解析受控内容对象与其关系。
7. 删除或撤销不假装召回已经交付的明文。清理本系统的缓存/索引和后续访问，按声明的保留规则处理物理内容。

首期共享固定版本、只读授权。持续同步、跨服务转授权和复杂派生许可均延后，但不得破坏这里的身份与来源规则。

## 10. 协议验收与冻结条件

后续实现需要独立的 conformance 包，至少包括：

- 有效/无效清单、CloudEvents、Descriptor 的固定向量，以及未知可选/必需能力案例。
- 对相同来源重复采集结果稳定、两个不同来源不会错误合并、序列化字节与摘要一致的性质验证。
- 缺对象、损坏对象、来源缺口、半行、文件替换、并发提交、提交后断线的故障案例。
- 旧 reader/新 writer、新 reader/旧 writer 的兼容矩阵。
- 两种 Agent 的实际格式语料和有效历史基线，包含压缩/回退/分支/并行调用。
- 发布内容闭包、私有来源引用隔离、撤销与读取交错的授权案例。

能通过本协议的 Capture/Revision 验收，不自动获得 Native Restore 能力。不同能力分开列明支持版本、验证方法和已知限制。
